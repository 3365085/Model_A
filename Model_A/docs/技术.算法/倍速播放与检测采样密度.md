# 倍速播放与检测采样密度

记录日期：2026-05-19

## 问题背景

Web 端支持对本地 MP4 进行播放速度控制。用户提出：项目检测模块依赖逐帧检测，如果播放速度变化，检测帧数和检测效果是否会变化。

## 当前链路判断

当前运行链路不是“每帧必检”。视频源按播放时钟推送预览帧，检测链路通过 latest-only 队列消费最新帧，并受 `detector_process_fps_cap` 限制。

关键代码依据：

- `src/defense/runtime/runner.py`：`_backend_capture_loop()` 按 `frame_period / playback_speed` 控制 MP4 读取节奏。
- `src/defense/runtime/runner.py`：`detection_bus.push(packet)` 按 `detect_interval` 推送检测帧。
- `src/defense/runtime/backend_pipeline.py`：`DetectionBus` 只保留最新待检测帧，慢检测会丢弃旧帧，避免预览被检测反压。
- `src/defense/runtime/runner.py`：`_preview_render_loop()` 独立渲染预览，并通过 overlay 时间匹配叠加检测结果。

## 影响分析

倍速播放时，同一真实时间内经过的视频内容变多，但检测处理上限不变。因此按“每秒视频内容”计算，实际检测采样密度可能下降。检测框仍然可能稳定，是因为预览帧保持流畅，overlay 有时间匹配、保持和插值机制；这不等价于检测算法效果完全无损。

低倍速播放时，同一段视频内容在真实时间里停留更久，检测器有更多机会处理相邻帧。对短暂目标、快速遮挡、短时裸头、安全帽变化、物理扰动连续确认、A3b 观察窗口等场景，低倍速可能提升检出稳定性。但收益有上限，不会超过原视频本身可提供的信息密度。

## 已观察现象

一次短测中，默认视频在 `desktop_rtx` 档位下：

- `1x`：约 14 至 15 个检测 overlay / 视频秒。
- `2x`：约 12 个检测 overlay / 视频秒。
- 预览保持约 24.8 fps，检测框显示稳定。

该观察说明倍速会影响检测采样密度；但样本较短，不能作为完整算法效果评估结论。

## 结论

播放速度会影响检测采样密度。高倍速可能降低对短时异常的覆盖率；低倍速可能提升离线复核时的检测覆盖率，但不能代表真实部署效果。

如果要评估算法能力，应使用固定视频时间采样策略或完整检测模式，而不是依赖 UI 播放速度。UI 倍速适合预览、调试和复核，不应作为正式检测效果评估的唯一依据。

## 后续建议

- 增加“检测采样密度”状态指标，例如每视频秒检测帧数、跳过帧数、latest-only 替换次数。
- 区分“预览倍速”和“检测策略”：预览可倍速，检测可选择固定视频时间采样或完整检测。
- 对关键算法评估引入离线基准脚本，按固定帧步长或逐帧运行，输出可复现实验报告。

## 待确认事项

- 不同视频类型、不同 GPU 负载和不同 `detector_process_fps_cap` 下的采样密度变化仍需系统实验确认。
- 倍速对 A3b、物理扰动连续确认、安全帽连续窗口的具体误检/漏检影响仍需用标注样本验证。
