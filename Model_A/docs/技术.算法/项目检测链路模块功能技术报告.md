## 1. 总体结论

从工程链路看，项目不是单一页面展示项目，而是具备完整的“Web 启动 -> 输入源采集 -> 检测推理 -> Module A A1-A4/A3b 分析 -> PPE 安全帽状态 -> overlay/status 推送 -> evidence 事件落盘”的闭环。

已从代码确认的闭环如下：

1. Web 服务入口由 `src/defense/web/server.py` 的 `main()` 启动，创建 `src/defense/web/fastapi_app.py` 的 `create_app()`。
2. 前端调用 `/api/start` 后进入 `src/defense/runtime/runner.py` 的 `MonitorEngine.start()`。
3. `MonitorEngine.start()` 创建 `PreviewBus`、`DetectionBus`，并启动采集线程 `_backend_capture_loop()`、检测线程 `_backend_process_loop()`、预览线程 `_preview_render_loop()`。
4. 检测线程通过 `src/defense/runtime/frame_processor.py` 的 `FrameProcessor.process()` 调用 `VideoDefensePipeline.process_frame()`。
5. `src/defense/pipelines/video_defense_pipeline.py` 的 `VideoDefensePipeline._run_detection()` 调用后端目标检测，再由 `DetectionROIProvider` 生成 ROI，最后调用 Module A。
6. `src/defense/module_a/process_pipeline.py` 的 `process_module_a()` 依次执行 A1、A2、A3、A3b、A4，并返回 `ModuleAResult`。
7. `FrameProcessor.process()` 同步生成 PPE 状态、展示跟踪框、分支卡片 `branch_cards`。
8. `MonitorEngine._after_processed()` 生成 overlay record、更新 status、合并 evidence 完成事件。
9. `src/defense/runtime/evidence.py` 的 `EvidenceSession.update()` 根据 `module_a`、`ppe`、`a3b` 三类通道生成事件证据。
10. 前端 `src/defense/web/static/index.html` 通过 `/api/overlay`、`/api/status`、`preview.mjpg` 和 WebSocket 显示画面、检测框、分支卡片、事件列表。

需要特别说明：用户提到的“rol 层”在代码中未发现对应命名实体；当前项目使用的是 `ROI` 层，即 `src/defense/module_a/types.py` 的 `ROI` 数据结构和 `src/defense/module_a/roi_provider.py` 的 `DetectionROIProvider`。本文按 ROI/检测区域层解释；如果业务上存在独立的 ROL 概念，未能从代码中确认。

## 3. 运行时帧流链路

### 3.1 运行时引擎

核心文件：`src/defense/runtime/runner.py`

核心类：`MonitorEngine`

关键函数：

- `MonitorEngine.start()`：校验输入源、停止旧运行、递增 `run_id`、预加载 `PipelineBundle`、创建 bus、启动三个线程。
- `_backend_capture_loop()`：从 `cv2.VideoCapture` 读取帧，向 `PreviewBus.publish()` 发布预览帧，按检测频率向 `DetectionBus.push()` 投递检测帧。
- `_backend_process_loop()`：从 `DetectionBus.pop_latest()` 获取最新检测帧，调用 `FrameProcessor.process()`，再进入 `_after_processed()`。
- `_preview_render_loop()`：从 `PreviewBus` 获取预览帧，按 `overlay_timeline` 选择最合适的 overlay，渲染 MJPEG。
- `_after_processed()`：更新 evidence、生成 overlay record、更新 status、写入 recent events。
- `get_overlay()`：对前端返回 `records`、`latest_seq`、`detector_ready`、`running` 等字段。
- `control_run()`：支持播放、暂停、seek、倍速设置；seek 时会更新 `source_epoch` 并清理 overlay timeline。

### 3.2 预览与检测解耦

核心文件：`src/defense/runtime/backend_pipeline.py`

核心类：

- `PreviewBus`：保存最新预览帧，用于画面持续刷新。
- `DetectionBus`：只保留最新待检测帧，旧帧被替换，避免检测线程跟不上时积压。

配置项：`configs/module_a_runtime.yaml`

- `runtime.detector_queue_policy: latest_only`
- `runtime.detector_process_fps_cap: 15`
- `runtime.preview_render_fps: 25`
- `runtime.overlay_match_window_ms: 180`
- `runtime.overlay_hold_ms: 550`
- `runtime.overlay_interpolate_ms: 400`
- `runtime.overlay_max_age_ms: 950`

工程判断：该设计的重点不是“每一帧都检测”，而是“预览连续、检测最新帧”。这能解释倍速播放下检测框仍可能看起来正常：检测队列会丢弃过期检测帧，overlay 也有 hold/interpolate 策略。

## 9. 倍速播放对检测链路的影响

相关文件：

- `src/defense/runtime/runner.py` 的 `_backend_capture_loop()` 和 `control_run()`
- `src/defense/runtime/backend_pipeline.py` 的 `DetectionBus`
- `configs/module_a_runtime.yaml` 的 `runtime.detector_process_fps_cap`

从代码可确认：

1. MP4 播放速度会影响采集线程读取帧的节奏。
2. 检测队列采用 latest-only 策略，检测线程忙时只处理最新检测帧。
3. 预览与检测解耦，因此画面可以流畅播放，而检测结果按检测线程能力更新。
4. overlay 具备 hold/interpolate/max age 策略，因此检测框在倍速播放下可能仍然看起来连续。

对检测效果的推断：

- 高倍速播放时，单位墙钟时间内输入帧推进更快；如果检测线程无法按同样速度处理，实际检测覆盖的视频时间密度会下降，A2/A3/A3b 这类依赖相邻检测帧变化的策略可能受影响。
- 低倍速播放时，单位墙钟时间内输入帧推进更慢；检测线程更容易覆盖更多视频帧，单帧目标框展示通常更稳定。但这不等价于算法效果必然提升，因为 A4 的 `AlertState` 当前 Web 路径主要使用帧窗口，而非真实时间窗口。

重要发现：

- `FrameProcessor.process()` 当前调用的是 `self.pipeline.process_frame(frame_640)`。
- `VideoDefensePipeline.process_frame()` 构造 `ModuleAInput(..., timestamp=0.0)`。
- `VideoDefensePipeline.process_envelope()` 才会传入 `envelope.capture_ts`。
- `AlertState.update()` 支持 `frame_ts` 时间感知窗口，但当前 Web 检测路径未直接使用 `process_envelope()`。

工程影响：

当前 Web 检测链路更接近“检测帧窗口语义”，不是严格“真实时间窗口语义”。因此倍速播放可能改变检测窗口覆盖的视频时间跨度。该问题是否需要修改为时间感知路径，需结合业务定义确认：如果告警语义要求“真实时间内 3/5”，应考虑让 Web runtime 走 `process_envelope()` 或显式传入 `video_time_s/source_time_s`；如果告警语义要求“检测帧序列内 3/5”，当前实现是自洽的。

## 11. 无法从代码中确认的事项

以下事项必须通过运行环境和样本实测确认，不能仅凭代码下结论：

1. 当前 GPU/TensorRT/CUDA 库是否在目标机器完整可用。
2. 当前模型权重对真实业务场景的精度、召回率、误报率。
3. A1-A4/A3b 各阈值是否适配所有业务视频。
4. 高倍速和低倍速播放对 A2/A3/A3b/A4 最终告警效果的真实影响。
5. `ROL` 是否为业务文档中的独立层，代码中未发现。
6. Web 当前使用检测帧窗口而非时间窗口，是否符合产品验收口径。
7. evidence 事件在真实长视频、多次 seek、暂停/恢复场景下的完整性。
8. 前端中文文案在不同终端/编辑器下存在乱码显示风险；例如 `configs/module_a_runtime.yaml` 和部分 Python 文件在 PowerShell 输出中出现中文乱码，需用编辑器和运行页面共同确认实际编码。

## 12. 建议后续验证清单

1. 使用真实样本分别以 `0.3x`、`1.0x`、`2.0x` 播放，记录 `frame_idx`、`video_time_s`、`raw_boxes_count`、`p_adv`、`a3b_display_score`、`ppe_tracks`、`overlay_seq` 的变化。
2. 增加 Web runtime 的采样密度指标，例如“每秒视频时间实际检测帧数”和“每秒墙钟实际检测帧数”。
3. 明确 A4 告警窗口业务语义：按检测帧窗口还是按真实时间窗口。
4. 若业务要求真实时间窗口，评估将 Web 检测路径从 `process_frame()` 切换到 `process_envelope()`，或在 `FrameProcessor.process()` 中传入 `FramePacket.video_time_s/source_time_s`。
5. 对 A3b 和 PPE 分支补充真实视频 smoke 测试，覆盖事件触发、overlay 展示、evidence 落盘。
6. 保持 `DetectionBus` latest-only 策略，但在 UI 中展示检测采样状态，避免用户误以为每个预览帧都经过检测。
